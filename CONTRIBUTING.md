# Contributing

Thank you for helping. This repository holds two things, and they take contributions
differently.

## The specification (`SPEC.md`, `schema/`, `fixtures/`, `vectors/`)

The specification describes what DunneNote does. It does not decide it, so a change to the
format itself happens in DunneNote first and arrives here with a new schema version
([SPEC.md §14](SPEC.md#14-versioning-and-changelog)).

What helps most:

- **An issue** when the specification is unclear, incomplete, or disagrees with a notebook
  DunneNote wrote. Attach the notebook, or the smallest one that shows the problem, if you
  can share it.
- **A pull request** that fixes wording, a broken link or an example, without changing what a
  Reader or Writer must do.

`schema/v18.sql` and the notebooks in `fixtures/` are generated by DunneNote
([fixtures/README.md](fixtures/README.md)). Please don't edit them by hand. The files in
`vectors/` are generated by this library, and `tests/vectors.rs` checks that they match it.

## The library and `dnfmt` (`crates/`)

Bug reports and pull requests are welcome. Before you open a pull request:

```sh
cargo fmt --all
cargo clippy --all-targets --locked -- -D warnings
cargo test --all --locked
```

`rust-toolchain.toml` pins the Rust version. Please keep it: fold v1 depends on that version's
Unicode tables. Dependencies are pinned to the exact versions DunneNote uses (see the comment in
`Cargo.toml`), so a dependency upgrade usually waits for DunneNote.

Anything that writes to a notebook must follow the
[writer checklist](SPEC.md#13-writer-checklist), and come with a test that verifies the result
(`assert_clean` in `tests/support/common.rs`). Anything that parses input from a notebook or an
imported file should also get a property test in `tests/properties.rs`.

Report security problems privately, as [SECURITY.md](SECURITY.md) describes.
